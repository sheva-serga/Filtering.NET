# FN1007 — Operator body uses untranslatable method

**Severity:** Warning

## What triggers it

The body of a `[FilterOperator]` lambda invokes a method that isn't in the EF Core translatable allow-list:

```csharp
[FilterOperator("eq")]
public static Expression<Func<string, string, bool>> Eq =>
    (column, value) => column == FormatNicely(value); // FN1007 — FormatNicely isn't translatable
```

## Why it matters

Untranslatable methods either trigger client-side evaluation (slow, defeats the point of LINQ-to-SQL) or fail at apply-time with a runtime `InvalidOperationException`.

## Allow-list

The seeded list covers the common cases: `string.Contains/StartsWith/EndsWith/Trim/Substring`, `Math.*`, `Enumerable.Any/All/Where/Select/…`, and `EF.Functions.{Like,ILike,Collate}`.

When the consuming project references `Microsoft.EntityFrameworkCore`, **any** `EF.Functions.*` invocation is accepted (so npgsql trigrams, full-text helpers, etc. don't trip the warning).

## Fix

Either re-shape the lambda to use a translatable method, or invoke an `EF.Functions.*` extension (when EF Core is referenced). For deliberate client-side helpers add `#pragma warning disable FN1007` and accept the perf trade-off.
